# 管理员完整备份与恢复设计

## 1. 背景与目标

FitGridWeb 已有 `ops/backup.sh` 和 `ops/restore.sh`，能够使用服务器密钥生成加密 PostgreSQL 逻辑备份并在显式指定的隔离数据库中恢复。但是现有能力只能通过 SSH 使用，未启用定时器，也不能从管理员页面生成、保留、下载或上传完整备份。

本次交付增加两条互补路径：

- 管理员页面提供便于日常使用的自包含加密备份和整库恢复。
- VPS 提供交互式一键便携备份脚本，生成与网页相同的文件。

现有 `ops/backup.sh` 继续承担使用服务器密钥的无人值守异机备份。用户级 JSON 导入导出仍只处理当前账号的网格产品，不能替代本设计中的完整数据库灾难恢复。

## 2. 范围

完整备份覆盖 PostgreSQL 中的全部 FitGridWeb 数据和结构，包括：

- Better Auth 用户、密码哈希、账号和数据库会话；
- 管理员与普通用户角色、状态；
- 邀请、网格产品和导入预检记录；
- PostgreSQL schema、RLS 策略和 Prisma 迁移记录。

备份不包含 VPS root 密码、nginx、sing-box、TLS 私钥、系统日志、Docker 镜像、`/etc/fitgridweb/fitgridweb.env` 或服务器备份密钥。换 VPS 时应用秘密和基础设施配置仍按运维手册单独迁移或重建。

网页不提供脱离恢复文件的“清空数据库”按钮。“清除和恢复”是不可拆分的整库替换动作：只有已上传、解密并验证成功的备份才能覆盖当前生产数据。

## 3. 方案选择

采用主机维护执行器，不让 Next.js 应用容器直接获得 Docker 控制权、数据库迁移角色或 PostgreSQL 客户端。管理员 API 只负责会话授权、重新验证、上传流控制、任务创建和状态读取；root 管理的 systemd 执行器只接受固定 schema 的受限任务，在主机上调用项目内固定脚本。

放弃以下方案：

- 应用容器直接运行 `pg_dump`/`pg_restore`：需要向公网应用注入数据库高权限凭据，而且应用无法安全停止自身。
- 网页只生成 SSH 命令：权限边界清晰，但没有实现用户要求的一键操作。

## 4. 管理员页面

管理员页新增“数据保险库”区域，与邀请和账号状态账本分区。视觉继续使用现有 TradingView 风格的深色画布、紧凑数据标签和明确状态色；危险操作使用红色边框与文字，但不使用大面积红色背景。区域的特征元素是一条可读的备份生命周期轨道，固定呈现“正在生成 → 正在加密 → 可以下载”。

### 4.1 创建备份

管理员点击“创建备份”后打开弹窗，必须填写：

- 当前管理员密码；
- 独立备份密码；
- 再次确认备份密码。

独立备份密码长度为 12–128 个字符，两次输入必须一致。当前管理员密码只存在于浏览器组件和当前 HTTPS 请求内存中，验证后立即丢弃；独立备份密码在应用内存之外只短暂写入受限任务秘密文件，执行器读取后立即删除。两类密码都不进入浏览器持久存储、数据库、审计日志或普通服务日志，弹窗关闭后同时清空页面状态。

服务端使用当前 Better Auth 会话确认管理员身份，并通过 Better Auth 的当前密码验证能力重新验证操作者。创建请求成功后页面轮询任务状态并依次显示：

1. `dumping`：正在生成；
2. `encrypting`：正在加密；
3. `ready`：可以下载。

同一时间只允许一个备份或恢复任务。客户端立即锁定按钮，服务端和主机执行器再次执行互斥检查，避免重复点击、并发标签页或重放请求造成并行维护任务。

### 4.2 历史备份

“创建备份”按钮下方展示最多 5 条已成功完成的便携备份，按创建时间倒序排列。每条显示：

- UTC 备份时间并按 Asia/Shanghai 转换显示；
- 文件大小；
- 下载按钮。

只有通过转储可读性、加密完成和文件摘要校验的文件才能加入历史列表。创建第 6 份成功备份后，执行器才删除最旧文件及其索引；失败或半成品不会占用历史名额，也不能触发旧备份删除。

下载由管理员授权接口发放短期、单次、绑定管理员与备份 ID 的令牌。备份文件不映射为 nginx 静态目录，路径和文件名都不能绕过授权直接访问。下载不会删除 VPS 上的副本。

### 4.3 上传与预检

恢复使用两阶段交互：

1. 管理员选择 `.fitgridbackup`，输入独立备份密码并上传；
2. 系统在隔离暂存目录中流式落盘、解密和预检，不修改生产数据库。

默认上传上限为 512 MiB，通过环境变量 `PORTABLE_BACKUP_MAX_BYTES` 调整。nginx 和应用端同时执行上限；应用使用流式写入，不调用会把整个文件读入内存的 `request.formData()`。文件超过限制、扩展名错误、摘要不匹配、密码错误、归档路径穿越、manifest 不兼容或 `pg_restore --list` 失败时，删除暂存文件并保持生产服务不变。

预检成功后页面展示备份时间、应用镜像版本、PostgreSQL 主版本、文件大小、用户数、产品数、邀请数和完整性结果。预检结果生成一个 10 分钟有效、绑定管理员 ID、上传摘要和请求 ID 的恢复挑战；不能替换挑战对应的上传文件。

### 4.4 整库恢复

最终确认要求管理员再次输入当前密码，并准确输入确认短语 `恢复全部数据`。服务端验证管理员、密码、恢复挑战、任务互斥和同源请求后，才创建主机恢复任务。

执行器按以下顺序工作：

1. 再次校验上传文件摘要、归档结构和 PostgreSQL 转储可读性；
2. 使用服务器 `backup.key` 生成仅用于本次操作的恢复前本地回滚快照；
3. 写入维护状态，停止 app 容器但保持 db 容器运行；
4. 终止数据库中的应用角色连接；
5. 使用迁移角色和 `pg_restore --clean --if-exists --no-owner --exit-on-error --single-transaction` 替换生产 schema；
6. 使用已部署应用镜像执行 Prisma migrations；
7. 删除恢复数据库中的全部 Better Auth session，使所有用户必须重新登录；
8. 启动 app 并等待容器健康，再检查本地与公网健康端点；
9. 删除上传文件、密码秘密文件和临时明文；保留不含秘密的任务结果。

恢复期间页面预计短暂失去连接。浏览器显示明确的维护提示并用退避策略轮询健康状态；应用恢复后读取最终任务状态。成功时跳转登录页。触发恢复的临时管理员可能不存在于恢复后的数据库，之后必须使用备份内的管理员账号登录。

任何恢复步骤失败时，执行器使用恢复前快照尝试回滚，再重新运行迁移并健康检查。回滚成功则恢复旧生产数据并报告原恢复失败；回滚也失败则保持维护状态，不反复自动重试，并在任务结果和 journal 中给出固定的 SSH 诊断命令。

## 5. 便携备份格式

文件名为 `fitgridweb-YYYYMMDDTHHMMSSZ.fitgridbackup`。格式采用 passphrase 模式的 age 认证加密，明文载荷是确定结构的 tar archive：

```text
manifest.json
database.dump
database.dump.sha256
```

`manifest.json` 不含用户名、密码、会话 token 或应用秘密，至少包含：

```json
{
  "format": "fitgridweb-portable-backup",
  "formatVersion": "1.0.0",
  "createdAt": "2026-09-03T06:30:00Z",
  "appImage": "ghcr.io/zhshy7713950/fitgridweb:sha-...",
  "postgresMajor": 17,
  "database": "fitgridweb",
  "counts": {
    "users": 2,
    "gridTrades": 24,
    "invitations": 1,
    "importPreviews": 0
  }
}
```

创建端先产生并验证 PostgreSQL custom-format dump，再写入 SHA-256，最后归档并加密。恢复端先由 age 完成认证解密，再拒绝软链接、绝对路径、`..` 路径、额外文件、重复文件和超限解压，随后验证 dump 摘要与 `pg_restore --list`。任何未识别的 major formatVersion 都必须拒绝，不能猜测兼容。

网页历史索引另存于 VPS，只包含随机备份 ID、文件基名、创建时间、文件大小、外层 SHA-256 和状态。索引不是恢复所必需；迁移到新 VPS 时仅凭 `.fitgridbackup` 和独立密码即可预检恢复。

## 6. 主机执行器与文件权限

安装器创建并启用：

- `fitgridweb-maintenance.path`：监视固定任务收件箱并触发执行；
- `fitgridweb-maintenance.service`：串行清空队列并执行允许的任务；
- `/var/lib/fitgridweb/admin-ops`：任务、状态和审计根目录；
- `/var/lib/fitgridweb/portable-backups`：最近 5 份便携备份。

应用容器只挂载最小的任务提交、上传、状态读取和备份只读路径；不挂载 Docker socket、`fitgridweb.env`、`backup.key` 或审计日志。主机执行器以 root 运行，但不接受任意命令、任意数据库 URL 或用户控制的输出路径。任务 ID 必须是服务端生成的 UUID，任务 schema 只允许 `backup`、`inspect-restore` 和 `restore`，所有路径通过真实路径检查限定在固定目录下。

备份密码使用单独的 `0600` 秘密文件传给执行器，不放在命令参数中；执行器读取后立即 unlink，并保证退出 trap 清理明文、上传密码和临时目录。任务状态采用原子 rename 写入，避免页面读取半写 JSON。

VPS 重启后 path unit 自动恢复监听。启动恢复逻辑只清理已确认未进入生产替换阶段的陈旧临时任务；如果检测到中断的恢复事务，则保持维护状态并要求人工检查，不能假定继续或回滚一定安全。

## 7. API 与授权边界

新增管理员 API：

- `POST /api/v1/admin/backups`：重新验证并创建备份任务；
- `GET /api/v1/admin/backups`：列出最多 5 份已完成备份；
- `POST /api/v1/admin/backups/{id}/download-token`：发放单次下载令牌；
- `GET /api/v1/admin/backups/{id}/download?token=...`：流式下载；
- `POST /api/v1/admin/restores/uploads`：流式上传并创建预检任务；
- `GET /api/v1/admin/maintenance/jobs/{id}`：读取任务阶段和安全错误；
- `POST /api/v1/admin/restores/{id}/confirm`：重新验证并确认整库恢复。

所有入口都要求 active admin、同源保护、现有限流器和无 ownerId。密码错误统一返回不泄露账号状态的信息。下载响应使用 `Cache-Control: no-store, private`、`Content-Disposition: attachment` 和内容嗅探保护。任务状态只向任务发起管理员或当前 active admin 暴露，响应不包含宿主机绝对路径和命令输出。

## 8. 审计

恢复会覆盖数据库，因此权威审计日志放在数据库之外的 root-only JSON Lines 文件，并同步进入 systemd journal。每条记录包含操作类型、管理员 ID、请求 ID、任务 ID、时间、备份摘要、状态和稳定错误代码；不包含用户名以外的个人业务数据，也不包含密码、Cookie、邀请 token、上传正文、数据库 URL 或完整命令输出。

备份创建、下载令牌发放、下载完成、恢复预检、恢复确认、回滚开始与结果都写审计记录。日志轮转由 logrotate 管理，默认保留 180 天。

## 9. 手动、网页和自动备份

新增 `/opt/fitgridweb/ops/backup-portable.sh`。root 交互运行时从 TTY 隐藏读取独立备份密码并确认，强制 12–128 字符，调用与主机执行器相同的备份库，输出兼容网页恢复的 `.fitgridbackup`，更新同一历史索引并遵守成功后最多保留 5 份的规则。密码不能通过命令参数传入，避免进入 shell history 和进程列表。

现有 `/opt/fitgridweb/ops/backup.sh` 保持非交互模式，使用 `/etc/fitgridweb/backup.key` 加密并复制到 `BACKUP_REMOTE_DIR`，用于真正的异机灾难恢复。它不写入网页最近备份列表，也不受 5 份便携备份限制。安装器只有在 `BACKUP_REMOTE_DIR` 指向有效异机挂载时才允许启用每日 systemd timer；未配置时必须报告“自动异机备份未启用”，不能把同机目录伪装成自动灾备。

## 10. 低资源与故障处理

- `pg_dump`、tar、age 加解密、SHA-256 和下载全部使用流，不能把 dump 或上传文件整体放入 Node.js 内存。
- 任务严格串行；备份或恢复运行时拒绝第二个维护任务。
- 创建任务前检查磁盘空间，要求可用空间至少为当前数据库估算大小的两倍再加 256 MiB；无法可靠估算时拒绝恢复并提示 SSH 检查。
- 临时文件与最终文件必须位于同一受控文件系统，最终发布使用原子 rename。
- 浏览器轮询使用退避且页面不可见时降低频率，不产生此前出现过的高频请求。
- 下载中断不删除服务端备份；上传中断清理不完整文件。

## 11. 测试与验收

自动测试遵循先失败后实现，至少覆盖：

- member、匿名用户和 disabled admin 不能使用任何维护 API；
- 管理员当前密码错误、备份密码过短或确认不一致时不创建任务；
- 客户端、API 和主机三层都阻止并发任务；
- 状态按 `dumping → encrypting → ready` 单向前进，失败状态可终止轮询；
- 历史只展示成功文件，按时间倒序，成功生成第 6 份后才删除最旧一份；
- 下载令牌过期、重放、管理员不匹配和备份不匹配时拒绝；
- 512 MiB 上限、流式上传、中断上传清理和路径穿越拒绝；
- 错误密码、篡改密文、非法 tar、未知格式和不可读 dump 均在维护前拒绝；
- 恢复挑战过期、上传被替换、确认短语错误和重新验证失败时不进入维护；
- 恢复前快照、app 停写、生产恢复、迁移、session 清除、健康检查顺序固定；
- 任一步骤失败触发一次回滚，回滚失败保持维护状态；
- `backup-portable.sh` 隐藏交互、两次密码一致性、格式兼容和五份保留；
- 安装/升级幂等生成 systemd、目录权限、nginx 上传限制和 logrotate 配置；
- 2 GiB 等价环境完成一次真实备份、下载、上传预检、整库恢复、重新登录和抽样网格重算。

生产验收必须在隔离或明确可清除的生产等价环境中完成。测试证明恢复成功之前，不能把“文件已生成”当作灾难恢复完成。
